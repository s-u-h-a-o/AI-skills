# 系统化调试

## 概述

随机修复浪费 time 并制造新 bug。快速补丁掩盖根本问题。

**核心原则：** 在尝试修复之前，始终先找到根因。修复症状是失败的做法。

**违反此流程的字面规定即是违反调试精神。**

## 铁律

```
未完成根因调查，不得进行修复
```

如果你还没完成第一阶段，就不能提出修复方案。

## 适用场景

对任何技术问题使用：
- 测试失败
- 线上 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**特别在以下情况更要用：**
- 时间紧迫（紧急情况容易诱使猜测）
- "就来一个快速修复"看起来很明显
- 你已经尝试了多次修复
- 上次修复不奏效
- 你还没有完全理解问题

**以下情况不能跳过：**
- 问题看起来很简（简单 bug 也有根因）
- 你很匆忙（仓促保证返工）
- 管理者要求现在马上修好（系统化比盲目试错更快）

## 四阶段法

必须在完成每个阶段后才能进入下一阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **认真阅读错误消息**
   - 不要跳过错误或警告
   - 它们往往包含了精确的解决方案
   - 完整阅读堆栈跟踪
   - 注意行号、文件路径、错误代码

2. **稳定复现**
   - 能否可靠地触发？
   - 具体步骤是什么？
   - 每次都会发生吗？
   - 如果无法复现 → 收集更多数据，不要猜测

3. **检查最近的变更**
   - 什么改动可能导致此问题？
   - Git diff、最近的提交
   - 新的依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复方案之前，添加诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置的传播
     - 检查每一层的状态

   运行一次收集证据，揭示问题出在哪
   然后分析证据，识别故障组件
   然后调查该特定组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== 工作流中的密钥：==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== 构建脚本中的环境变量：==="
   env | grep IDENTITY || echo "IDENTITY 不在环境中"

   # 第 3 层：签名脚本
   echo "=== 钥匙串状态：==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **结果揭示：** 哪一层出问题（密钥 → 工作流 ✓，工作流 → 构建 ✗）

5. **追踪数据流**

   **当错误位于深层调用栈中：**

   参见本目录下 `root-cause-tracing.md` 的完整逆向追踪技术。

   **快速版：**
   - 错误值源自哪里？
   - 什么调用传递了这个错误值？
   - 一直向上追踪直到找到源头
   - 在源头修复，而非在症状处修复

### 阶段 2：模式分析

**修复前先找到模式：**

1. **寻找正常运行的实例**
   - 在同一代码库中定位类似的正常工作代码
   - 什么与出错代码类似但却正常工作？

2. **对比参考实现**
   - 如果正在实现某个模式，完整阅读参考实现
   - 不要略读——逐行阅读
   - 在应用前完整理解该模式

3. **识别差异**
   - 正常工作与出问题之间有何不同？
   - 列出每一个差异，无论多小
   - 不要假设"那不可能有影响"

4. **理解依赖**
   - 这还需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它做了什么假设？

### 阶段 3：假设与测试

**科学方法：**

1. **形成单一假设**
   - 清晰陈述："我认为 X 是根因，因为 Y"
   - 写下来
   - 要具体，不要模糊

2. **最小化测试**
   - 做出尽可能小的修改来测试假设
   - 一次只变一个变量
   - 不要同时修复多个东西

3. **验证后再继续**
   - 奏效了？→ 阶段 4
   - 没奏效？形成新假设
   - 不要在上面叠加更多修复

4. **当你不懂时**
   - 说"我不理解 X"
   - 不要假装知道
   - 寻求帮助
   - 做更多研究

### 阶段 4：实施

**修复根因，而非症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 尽可能自动化测试
   - 没有测试框架可以用一次性测试脚本
   - 修复前必须有
   - 使用 `superpowers:test-driven-development` skill 编写合适的失败测试

2. **实施单一修复**
   - 针对已识别的根因
   - 一次一个修改
   - 不要"顺便"优化
   - 不要捆绑重构

3. **验证修复**
   - 测试现在通过了？
   - 没有其他测试被破坏？
   - 问题确实解决了？

4. **如果修复不奏效**
   - 停止
   - 数一数：你尝试了多少次修复？
   - 如果 < 3 次：返回阶段 1，利用新信息重新分析
   - **如果 ≥ 3 次：停止并质疑架构（看下面第 5 步）**
   - 不要在未经架构讨论的情况下尝试第 4 次修复

5. **如果 3 次以上修复失败：质疑架构**

   **表明架构有问题的模式：**
   - 每次修复都在不同的地方暴露新的共享状态/耦合/问题
   - 修复需要"大规模重构"才能实现
   - 每次修复都在别处产生新症状

   **停止并质疑基础：**
   - 这个模式根本上合理吗？
   - 我们是否"仅仅出于惯性"在坚持它？
   - 我们应该重构架构还是继续修复症状？

   **在尝试更多修复之前与人类伙伴讨论**

   这不是失败的假设——这是错误的架构。

## 红旗——停止并遵循流程

如果发现自己在想：
- "先来一个快速修复，后面再调查"
- "试试改 X 看看行不行"
- "加多个改动，运行测试"
- "跳过测试，我手动验证"
- "大概就是 X，让我修它"
- "我不完全理解但这可能行"
- "模式说 X 但我换个方式适配"
- "以下是主要问题：[未经调查就列出修复方案]"
- 追踪数据流之前就提出解决方案
- **"再试一次修复"（当已经尝试了 2 次以上）**
- **每次修复都在不同地方揭示新问题**

**以上所有都意味着：停止。返回阶段 1。**

**如果 3 次以上修复失败：** 质疑架构（参见阶段 4.5）

## 你的方式出错了——人类伙伴的信号

**注意这些重定向：**
- "这不是在发生吗？"——你未经验证就假设了
- "它能否向我们展示……？"——你本应添加证据收集
- "别猜了"——你在不理解的情况下提出修复方案
- "深究这个"——质疑基础，而非仅质疑症状
- "我们卡住了？"（沮丧的语气）——你的方法不起作用

**当看到这些：** 停止。返回阶段 1。

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程处理简单 bug 很快。 |
| "紧急情况，没时间走流程" | 系统化调试比猜测试错更快。 |
| "先试一下，然后再调查" | 第一次修复定下模式。从开始就做对。 |
| "确认修复有效后我再写测试" | 未经测试的修复不能持久。先测试才能证明。 |
| "一次性多改几个更省时间" | 无法隔离哪个生效了。还产生新 bug。 |
| "参考太长，我适配一下模式就行" | 部分理解保证出 bug。完整阅读。 |
| "我看到问题了，让我修它" | 看到症状 ≠ 理解根因。 |
| "再试一次修复"（2 次失败后） | 3 次以上失败 = 架构问题。质疑模式，不要再次修复。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 寻找正常实例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或提出新假设 |
| **4. 实施** | 创建测试、修复、验证 | bug 解决、测试通过 |

## 当流程揭示"没有根因"

如果系统化调查揭示问题确实是环境性的、时序依赖的或外部的：

1. 你已经完成了流程
2. 记录你调查了什么
3. 实施适当的处理（重试、超时、错误消息）
4. 添加监控/日志以供将来调查

**但：** 95% 的"没有根因"案例是不完整的调查。

## 辅助技术

这些技术是系统化调试的一部分，在本目录下可用：

- **`root-cause-tracing.md`** — 沿调用栈逆向追踪 bug 找到原始触发器
- **`defense-in-depth.md`** — 在找到根因后在多层添加校验
- **`condition-based-waiting.md`** — 用条件轮询替代任意超时

**关联 skill：**
- **superpowers:test-driven-development** — 创建失败测试用例（阶段 4，步骤 1）
- **superpowers:verification-before-completion** — 在声称成功前验证修复是否生效

## 实际效果

来自调试记录：
- 系统化方法：15-30 分钟完成修复
- 随机修复方法：2-3 小时的盲目试错
- 一次修复成功率：95% vs 40%
- 引入新 bug：接近零 vs 常见
