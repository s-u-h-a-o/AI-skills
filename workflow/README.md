# 🔄 开发流程

开发流程类 skill，覆盖从需求分析到代码合并的完整生命周期。

## Skill 清单

### `brainstorming`

在编写任何代码之前，先探索用户意图、需求和设计方案。所有创造性工作（新功能、组件、行为修改）的前置步骤。

> **场景示例：** 用户说“我想加一个搜索功能” → 不直接写代码，先问清楚：搜索什么内容？实时搜索还是按钮触发？需要高亮匹配吗？有筛选条件吗？确认后再动手。

### `writing-plans`

拿到需求或 spec 后，在写代码前先撰写多步骤实现计划。

> **场景示例：** 接到一个“用户权限系统”需求 → 先写计划：1) 定义角色和权限模型 2) 创建权限校验中间件 3) 改造路由守卫 4) 编写测试 5) 文档更新。每一步验证点明确后再执行。

### `executing-plans`

在独立 session 中按实现计划逐步执行，每步有 review checkpoint。

> **场景示例：** 上一轮写好了权限系统实现计划 → 新开一个 session，按计划步骤逐个执行，每完成一步停下来 review，确认无误后继续下一步。

### `finishing-a-development-branch`

功能开发完成、所有测试通过后，决定如何合并：直接 merge、创建 PR、或清理丢弃。

> **场景示例：** 一个 feature 分支开发完，6 个 commit 历史杂乱 → 提供选项：squash merge 到 main、rebase 整理后提 PR、或保留历史直接 merge，并说明各选项的适用场景。

### `requesting-code-review`

完成重要任务或合并前，系统性审查代码：正确性、可读性、边界情况、安全风险。

> **场景示例：** 写完一个支付模块准备合并 → 检查金额计算精度、错误处理是否完整、是否有 SQL 注入风险、loading 和 error 状态是否覆盖，输出审查报告。

### `receiving-code-review`

收到 code review 反馈后的处理指南：不盲目接受、不抵触拒绝，用技术分析验证每条建议。

> **场景示例：** Reviewer 说“这里用 for 循环不如用 reduce” → 不直接改也不直接拒绝，分析：数据量多大？可读性哪个好？性能差异？有理有据地回复或改进。
