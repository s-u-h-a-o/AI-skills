# 接收 Code Review

## 概述

代码审查需要技术评估，而非情感表演。

**核心原则：** 实现前验证。假设前先问。技术正确性优先于社交舒适。

## 响应模式

```
收到 code review 反馈时：

1. 阅读：完整阅读反馈，不立即反应
2. 理解：用自己的话重述需求（或提问）
3. 验证：对照代码库实际情况检查
4. 评估：对此代码库技术合理吗？
5. 响应：技术确认或有理有据的反驳
6. 实现：一次一个条目，逐个测试
```

## 禁止的响应

**永远不要：**
- "你说得完全对！"
- "好观点！" / "极好的反馈！"（表演性的）
- "让我现在就实现它"（验证之前）

**代之以：**
- 重述技术要求
- 提出澄清问题
- 如果错了用技术推理反驳
- 直接开始工作（行动胜于言语）

## 处理不清晰的反馈

```
如果任何条目不清晰：
  停止——先不要实现任何东西
  对不清晰条目寻求澄清

原因：条目可能相关。部分理解 = 错误实现。
```

## 来源特定处理

### 来自 human partner
- **可信**——理解后实现
- 范围不清晰时仍要询问
- 无表演性同意
- 跳过直接行动或技术确认

### 来自外部审查者
实现前：
1. 检查：对此代码库技术正确吗？
2. 检查：会破坏已有功能吗？
3. 检查：当前实现的原因？
4. 检查：在所有平台/版本上工作吗？
5. 检查：审查者了解完整上下文吗？

如果建议看起来错误：用技术推理反驳。
如果无法轻松验证：说出来。
如果与 human partner 之前的决定冲突：先停下讨论。

## YAGNI 检查

如果审查者建议"正确实现"：
- 在代码库中 grep 实际使用
- 如果未使用："这个端点没被调用。移除它（YAGNI）？"
- 如果被使用：那就正确实现

## 实现顺序

对多条目反馈：
1. 先澄清不清的内容
2. 然后按此顺序实现：阻塞性问题 → 简单修复 → 复杂修复
3. 每个修复单独测试
4. 验证无回归

## 何时反驳

以下情况反驳：
- 建议破坏已有功能
- 审查者缺乏完整上下文
- 违反 YAGNI（未使用的功能）
- 对当前技术栈技术上不正确
- 存在遗留/兼容性原因
- 与 human partner 的架构决策冲突

**如何反驳：** 用技术推理，非防御性。提具体问题。引用工作的测试/代码。

## 确认正确反馈

反馈正确时：
```
✅ "已修复。[简要描述改动]"
✅ "抓得好——[具体问题]。在 [位置] 修复了。"
✅ [直接在代码中修复并展示]

❌ "你说得完全对！"
❌ 任何感激表达
```

**为什么不说谢谢：** 行动胜于言语。直接修复。代码本身展示你听到了反馈。

## 优雅地纠正自己的反驳

反驳错了时：
```
✅ "你是对的——我查了 [X]，确实 [Y]。现在实现。"
❌ 长道歉、辩护为何反驳、过度解释
```

陈述纠正，继续前进。

## 常见错误

| 错误 | 修复 |
|------|------|
| 表演性同意 | 重述需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 不测试就批量处理 | 一次一个，逐个测试 |
| 假设审查者是对的 | 检查是否会破坏东西 |
| 避免反驳 | 技术正确性 > 舒适 |
| 部分实现 | 先澄清所有条目 |

## 底线

**外部反馈 = 需要评估的建议，不是需要遵循的命令。**

验证。质疑。然后实施。

不做表演性同意。始终技术严谨。
